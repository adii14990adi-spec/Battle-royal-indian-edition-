Clips are **discovered**, never invented: 74 FBXs, each with exactly one real

| CrouchWalk | 9 | Death | 7 |

The eight required gameplay categories (Idle, Walk, Run, Jump, Crouch, Aim,
Shoot, Reload) all have ≥1 real clip. "Other available categories" (Sprint,
Fall, CrouchWalk, Aim, RifleIdle, RifleRun, Shoot, Reload, WeaponSwitch, Melee,
Death) are covered by the same deterministic assignment.

**What changed**

* Added `Assets/Editor/CharacterAnimationIntegration.cs` — a headless,
  deterministic builder callable from a menu item or
  `-executeMethod ...BuildFromCommandLine`. It scans `Assets/Animations/` and
  the upload folder, reads imported `AnimationClip` sub-assets, deduplicates by
  clip reference and by SHA-256 source hash, assigns **one** clip per category
  using canonical name preference (e.g. `walking.fbx` beats `strafe (2).fbx`),
  verifies both Avatars and skinned meshes, and rebuilds each character's
  Animator Controller. No FBX is written; no incompatible rig is forced.
* Fixed `AnimationImportService.RegisterExistingAnimationAssets`: it used to
  overwrite the shared default for a category on *every* clip in unspecified
  `AssetDatabase` GUID order. It now ranks candidates deterministically and
  preserves an existing deliberate assignment.
* Fixed `ProjectValidator.CheckBlenderPipeline`, which looked for character
  sources in the non-existent `Assets/Art/Characters` and always reported
  "no shippable character source is committed yet". It now checks
  `Assets/Characters/`.
* Added `ProjectValidator.CheckCharacterAnimationAssets` — Editor-only checks
  for stable GUIDs, valid Humanoid Avatars, discovered clips, config references
  and generated controllers.
* Wired the headless builder into `unity.yml` (after Configure, before
  EditMode/PlayMode tests and project validation) and into `build.yml`
  (before the APK build), so a licensed CI run actually includes the generated
  config and controllers in the project/package.
* Added `.gitkeep` + ignore rules for the generated
  `Assets/AnimationControllers/` and `Assets/AvatarMasks/` folders, so generated
  outputs are never committed twice.
* Corrected stale "this repo commits no `.meta` files" comments in C#, docs
  and `.gitignore` (no longer true after PR #25).

Animator Controller parameters, states, transitions and the UpperBody layer
were **inspected, not rewritten**: `AnimatorControllerBuilder` already creates
10 parameters, the locomotion states, the one-shot triggers, the Death state,
and the `UpperBody` layer with an AvatarMask, and it skips states whose clips
are missing. The new builder uses it as-is.

## 5. PR #25 integration conflict found and fixed

Six turn clips (`turn 90 left/right`, `turn left`, `turning right 45 degrees`,
`crouching turn 90 left/right`) are one-shots with `loopTime: 0` in the
committed metadata. `MixamoImportSettings.WantsLoop` classified them as
`Walk`/`Crouch` cycles (default loop = true) and
`OnPreprocessAnimation` would silently turn them into infinite loops on every
import, disagreeing with the committed `.meta`. The fix is in code (so it
survives the metadata sync): `"turn"` was added to `ForceOneShotTokens`, and
EditMode + Python tests now pin all six names. Loop flags are now consistent
across all 74 metas and the C# rules.

older Chromebook with limited storage. Practical options, in order:

1. **GitHub Actions with a properly licensed Unity environment — already
   working.** `unity.yml` uses Buildalon `unity-setup` +
   `activate-unity-license` on a native `ubuntu-24.04` host runner (named-user
   licences bind to machine identity, so containerised activation is
   unreliable). The Personal licence secrets are already configured; the PR
   event ran Configure → **Build Character & Animation Integration** →
   EditMode tests → PlayMode tests → `ProjectValidator.ValidateAll`, all
   green. No local machine, no PC and no Chromebook storage needed. The same
   workflow builds an APK on `push` / `workflow_dispatch(build_apk=true)`;
   the PR event deliberately skips that step. Unity 6 Linux Editor requires
   x86_64 with SSE2, OpenGL 3.2+/Vulkan, ≥8 GB RAM recommended, and Ubuntu
   22.04/24.04; the runner provides that and frees disk space before
   installing the Editor and Android module.
2. **Compatible external Windows/Linux machine — most reliable if available.**
   A friend's desktop/laptop with Unity 6000.0.85f2 + Android Build Support,
   x86_64, ≥8 GB RAM and roughly 10–15 GB free (Editor ~6 GB + Android
   module + project `Library/`). Run the menu item and the manual checks in
   §9. This can also produce a `.ulf` licence file for CI if needed.
3. **The Chromebook — do NOT install Unity before checking.** Unity's Linux
   Editor requires an x86_64 CPU with SSE2, a supported Ubuntu X11/Wayland
   desktop with OpenGL 3.2+/Vulkan, ≥8 GB RAM recommended, and several GB of
   free disk. Most older Chromebooks have 2–4 GB RAM, 16–32 GB eMMC with far
   less free, and Crostini GPU support that does not expose Vulkan; ARM-based
   Chromebooks are not a supported Editor platform. Check **first** with
   `free -h`, `df -h`, `uname -m`, `lscpu`, and `glxinfo -B` / `vulkaninfo`
   inside Crostini, and confirm at least ~15 GB free and 8 GB RAM. If any
   check fails, use option 1 or 2 instead — the low-storage Chromebook should
   only ever be used for the browser/GitHub side of the workflow.
4. **Android/Termux** can run the Python static validators and inspect the
   repo, but cannot host the Unity Editor (no supported x86_64 Linux desktop
   GPU stack, no Unity Editor for Android). It is useful for reviewing PRs and
